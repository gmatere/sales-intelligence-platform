Overview / Ingest & Entity Resolution

8.9M records · 50 columns

Ingest & Entity Resolution

The dataset describes machines. A sales team needs companies. Everything difficult about this project lives in that gap.

The dataset is not what the brief implied

Profiling the first 8 MB settled the product direction before any code was written. It is not company data — it is internet scan records, one row per exposed service on an IP address. That makes it intent data, not fit data: almost nothing about company size or industry, a great deal about what is broken right now.

The trap

The org field names whoever registered the IP block — not the company using it.

Google LLC         2,745,419   30.8%
Incapsula Inc      1,778,843   20.0%
Cloudflare, Inc.     302,449
Amazon.com, Inc.     287,584

Group by org and your top prospects are Google, Imperva and Amazon — worthless to a rep and instantly disqualifying. So the entity key is the registrable domain (eTLD+1) from reverse-DNS hostnames, with the TLS certificate CN as a secondary anchor. org is used only to match the infrastructure denylist.

Why it streams

The source is 12.36 GB compressed and ~74 GB decompressed — a 6.03× ratio — on a box with about 64 GB free. It does not fit. zstd -d fails outright, so decompression is incremental and the JSON is never materialised. Memory stays flat regardless of input size.

The design decision mattered more than the constraint. Ingest is a pure projection — no scoring, no filtering, no business logic. So the one expensive read produces a reusable artifact, and every later change to scoring reruns against Parquet in seconds instead of re-reading 74 GB.

The IPv6 gap, and why it was left alone

Shodan fills ip_str for IPv4 and ipv6 for IPv6, leaving the other null. The ingest projects ip_str only — so IPv6-only services arrive with no address at all. That is 106,419 records, 1.19% of the source.

The instinct is to fix the data. The better first move was to measure what the gap actually costs:

81,94577% — no identity at all, already dropped
24,383Attribute and score normally
1.6%Of entities affected at all

Three quarters cost nothing: they have no hostname and no certificate CN either, so int_entity_hosts already discards them for lack of any identity. The rest work normally — because entity resolution keys on hostnames, not addresses. A host named mail.acme.com resolves to acme.com whether or not its address was captured.

So a fifth re-ingest was declined. The only residual effect was that count(distinct ip) undercounted estate size for 3,570 entities, which feeds the ICP size band — patched by falling back to hostnames in the distinct count. And there is no display cost, because the export drops every IP address by design. Forty minutes of wall clock, for a field nothing downstream depended on, against a fixed deadline. Recorded as D17.
Found by a test that was itself wrong. A not_null test on ip failed with 106,419 rows. The assertion was wrong, not the data — Shodan does not guarantee an IPv4 address. Replaced with assert_hosts_are_identifiable, which tests the weaker claim that matters: every host must have an address or a name. Its thresholds warn at the measured baseline and error above 100,000, so the current state becomes a canary for the source changing shape.

What it cost us

Truncated Parquet counted as complete. Shards were written straight to their final filename. Parquet writes its footer last, so a crash mid-write left a truncated file that the resume glob counted as done — silently skipping 100,000 records. Found by accident: reading the output directory mid-run raised No magic bytes found at end of file part-00006.parquet. Fixed with a staged write to .part-NNNNN.inflight and an atomic rename.

Transform & Scoring

Every deterministic decision lives in dbt on DuckDB — grouped by what it decides, not by table. These are set operations over columns; they need to be readable by someone who didn't write them, and tested as part of the build rather than by a suite someone remembers to invoke.

Four of the 48 tests guard failures that would actually cost something: infrastructure reaching a rep's list, unclassified entities being treated as prospects, honeypots surviving into the entity table, and scores drifting outside their range. The rest are schema hygiene.

Why five rule families, not one denylist

125,037 of 252,078 entities are excluded here. A curated list of provider names cannot reach the long tail of regional hosts — there are thousands of them, and adding the ones visible in a sample would overfit to that sample. So four behavioural heuristics sit alongside the list, each catching a different shape of infrastructure.

reverse_dns_zone — definitional

The entity is a .in-addr.arpa zone. Not a company by construction; no judgement required.

seed_list — ~70 named providers

Matched against normalised org strings, because the source carries the same company under several spellings — Incapsula Inc and Incapsula Inc. are 1.8M and 62k records respectively.

cloud_tag_volume — scale + cloud

cloud_host_ratio ≥ 0.9 AND n_hosts ≥ 50. Catches providers absent from the seed list. Both numbers chosen by inspection, not tuned — the LLM tier absorbs the imprecision.

sequential_hostnames — machine naming

srv12., vps-104. — customer-premises equipment is machine-named throughout, while municipal and ministry estates are small and hand-named.

port_diversity — multi-tenancy

n_hosts ≥ 20 AND n_ports ≥ 20. A single company rarely exposes twenty distinct services across twenty hosts; a shared host does.

Everything else → the model

127,041 entities survive the rules. They are not "companies" — they are unresolved, and that distinction is the whole design.

Prefer an extra model call to a silent exclusion. The sequential-name threshold was raised from 0.6 to 0.8 after sampling: two random samples of 25 excluded entities each contained one false positive — esteri.it at 0.64 (Italian Ministry of Foreign Affairs) and hajnowka.pl at 0.62 (a Polish municipality) — while every unambiguous ISP sat at 0.79–1.00. An excluded company is never reviewed and never recovers; an extra classification costs a fraction of a cent. That asymmetry sets the threshold.

Two scores, deliberately not one

Intent — how urgently they need help: exploitation probability, critical CVEs, exposed datastores, remote access, end-of-life software, certificate state, TLS posture. Fit — how well they match the ICP: estate size band, whitespace, real estate, multi-market presence, security maturity. Crossed into tiers A/B/C/D, plus R - needs review, U - unclassified and X - not a prospect.

Every component is kept as its own column, so the weights can be refitted against real outcomes later — and so a rep can disagree with a ranking by seeing what drove it.

Why EPSS, not CVSS or CVE counts

Every CVE in this dataset is version-inferred, never tested. Shodan matches a detected version against advisories; verified was false on 100% of 7,066 sampled CVE entries. So a host reporting 99 CVEs may have every one of them patched.

HostMax CVSSEPSSUrgency
Host A9.80.99999Being exploited now
Host B9.80.01225Effectively dormant

Identical severity, completely different urgency. A CVSS-ordered list treats them as equivalent. EPSS is a published probability about the vulnerability rather than an inference about this host, so it survives the same uncertainty.

Tier A filled with hosting providers. The first build's top 20 were Beget, Forpsi, startdedicated, vps-10, hostsila and the reverse-DNS zone 64.in-addr.arpa — all scoring 90 fit and 100 intent, because a multi-tenant estate accumulates every finding belonging to every tenant. The scores were correct; the inference drawn from them was not. The tiering logic read "rules found no evidence of infrastructure" as "confirmed company". No test caught it — the SQL was right and every schema test passed. Fixed by gating tiers on classification status.

Overview / Classification

6 classes · 3,000 classified

Classification

The LLM answers exactly one question: is this entity a real company, or is it infrastructure? Everything else in the pipeline is SQL.

Why a model is here at all the asymmetry

The boundary is set by an asymmetry, not by taste.

Rules can prove an entity is infrastructure — a seed match, a reverse-DNS zone, machine-named hosts across a large estate. Nothing can prove it is not. A regional hosting provider nobody has heard of looks exactly like a small business until someone reads the name.

So rules settle the provable half, and anything unresolved sits in U - unclassified and cannot reach a rep until the model adjudicates it.

end_customer_companyhosting_or_cloud cdn_or_security_vendorisp_telco government_or_educationunknown

How it runs

Tool-use against a fixed schema — never free text. Three retries with exponential backoff, concurrency 8, resume keyed on the (prompt version, model) pair, and a dry-run estimator that prices the work before spending and reports whether caching will engage.

Every call appends a trace: prompt version, model, decision, confidence, input / output / cached / cache-write tokens, cost, latency, attempt, error.

The funnel is the cost model see Cost Model

The bigger lever is the signal filter, not the rules. An entity with no security findings is not a prospect whether or not it is a real company, so classifying it buys nothing — and that filter is a WHERE clause on an aggregate, not a model call.

A school was silently dropped from the market. entity_class was typed str; the permitted values lived only in the tool schema's enum, which is advisory without strict: true. One call in 3,000 returned education instead of government_or_education — a Brazilian school, correctly named, at confidence 0.9 — and the tier logic matches class names exactly, so it fell through to X - not a prospect with nothing recording it. Fixed at both layers: entity_class is now a Literal that raises and retries, and the export refuses to run on any unrecognised class rather than bucketing it.

Overview / Serving & App

1,005 organisations

Serving & App

A curated Parquet and a Streamlit app that performs no inference and holds no credentials.

The boundary between pipeline and product

Three things happen in the export and nowhere else. Classification verdicts are merged in, so tiers can finally be assigned. Raw IP addresses are dropped — a rep needs the company, the finding and the reason to call, never an address. And per-call telemetry is joined on, so the app can show the real trace of the decision.

The export filters to exactly one (prompt version, model) configuration: the one the eval measured.

Three questions per account

QuestionAnswered by
Why this accountFit score, with every scoring component shown
Why nowFindings, each tagged with its evidence class
What do I sayDrafted outreach — cold email, InMail, or call script

The evidence distinction

Observed — seen directly in the scan. Tested — confirmed by an active probe. Inferred — implied by a version banner; the software is confirmed, the vulnerability is not. Collapsing those is how a rep ends up asserting a vulnerability that was never confirmed.

A generated email made a false technical claim. The draft asserted "you are running Apache httpd, a version associated with CVE-2015-0235". CVE-2015-0235 is GHOST — a glibc bug, not an Apache one. Both values came from arg_max(..., top_cve_epss) but were picked independently, so they can come from different services on the same host. Every value was correct; the sentence was not. Caught by reading three generated openers aloud. The opener no longer asserts the product alongside the CVE — it cites the finding, states that it is inferred, and asks the recipient to confirm.
The outreach is templated, not generated. An LLM would write better prose, but the binding constraint is accuracy: every claim must trace to an observed fact, and hedging on version-inferred CVEs must be exact. Template assembly guarantees that; generation would need its own eval to guarantee it. Logged as the next increment, not skipped by accident.

Evals & Measured Quality

75 hand-labelled entities, two batches, so a prompt tuned on the first is scored on the second. The most useful thing this eval did was prove itself wrong — twice.

Shipped: v4 on Sonnet 5 current

Precision on end_customer_company governs deployment — not accuracy. A false positive puts a hosting provider in a rep's call list; they phone a datacenter about its customers' vulnerabilities and never trust the tool again. A false negative removes a company from the market invisibly — costly, but recoverable.

Reversal one: 25 examples produced a confident wrong answer

At n=25, v3-on-Haiku measured 0.750 precision, ranked first of three, and the write-up argued explicitly against Sonnet at 0.500 — that Sonnet "commits where Haiku hedges", and decisiveness is the wrong disposition when a wrong commitment reaches a salesperson.

At n=75 the ordering inverted completely: Haiku last at 0.385 held-out, Sonnet first at 0.667. Nothing changed but the number of labels.

The caveat was already written, before the reversal — that support of 6 made one row worth 0.25 of precision, and that only one comparison was defensible. It turned out to be the only reliable line in that table. That is the argument for writing a limitation down when you notice it rather than after it embarrasses you.

Reversal two: one cell of the grid had never been run

v4 existed to clear Haiku's 4,096-token cache floor — but it also carried three content changes. Those were only ever tested on Haiku, because a Haiku cache floor was the point. When the first reversal moved the shipped model to Sonnet, v4-on-Sonnet was never tested.

Running it cost $0.28 and it won on every metric. Recall decided it, not precision: the held-out precision gain of 0.060 is less than one row and sits inside the measured noise, while recall moved 0.444 → 0.722 — five more real companies out of eighteen, with fewer false positives. Judging on precision alone would have called it a tie and shipped the worse configuration.

Both times the recommendation changed, production was re-run rather than leaving a conclusion the evidence no longer supported.

The noise floor underneath all of it

A billing mistake left two independent classifications of the same 3,000 entities under the same prompt and the same model. That makes the disagreement between them a direct measurement.

Held-out support is 12, so one row moves precision by 0.083 — and the gap between the best and worst configuration is a few rows, the same order as a model's disagreement with itself. The honest claim is "best measured so far", not "best".

Caching, not model choice, is the dominant term. The shipped Sonnet configuration is cheaper per call than uncached Haiku, despite triple the list price.

Caching failed silently, and four diagnoses all failed the same way

The minimum cacheable prefix is model-dependent and non-monotonic — Haiku 4.5 needs 4,096 tokens where Opus 5 needs 512. Below the floor nothing caches, the request still succeeds, and the cache fields just return zero.

Two compounding errors. The floor applies to the cacheable prefix — tools plus system, everything before the breakpoint — not to total input. And every attempt derived the prefix instead of observing it: from chars-per-token, then by subtracting an estimated message size from an observed total, then from a purpose-built script that did the same subtraction in tokens. That script over-reported by ~315 tokens — enough to report v3's prefix as 86 above a floor it was ~230 below.

Each estimate was within about 5%. Against a gradient, a 5% error means a 5% wrong answer. Against a hard cutoff it puts you confidently on the wrong side. The fix was one real API call reading cache_creation_input_tokens back — a fraction of a cent, two minutes. Which is why a longer prompt costs 2.5× less.
The production run was billed twice. The first Sonnet run wrote results before --model was recorded, so those rows carry model: null. The rerun's resume key is the (prompt_version, model) pair — correctly — which matched none of them, so all 3,000 were classified again. A key change is a migration: rows written under the old key are invisible to the new one, and "resume" silently becomes "restart". It cost ~$10.60 and produced the self-consistency measurement.

Overview / Known Limitations

36 live entries

Known Limitations

The six that change how you should read the output. Full list by layer in the repo — 36 live entries, plus the solved ones kept because the failure modes generalise.

LimitationWhy it matters
Every CVE is version-inferred, never tested verified was false on 100% of 7,066 sampled entries. Scoring leads on EPSS instead, and outreach hedges accordingly.
Tier A holds 818 of 1,005 accounts 81%. The queue is pre-filtered to entities with a finding, so urgency stops discriminating. Ranking within the tier is still correct; the label carries no information.
The model disagrees with itself on 4.5% of entities Measured across two identical runs of 3,000. It is the noise floor under every eval number here.
75 examples, one labeller, no adjudication Support of 18 overall, 12 held-out. At least two labels are probably wrong — 3cx.ae is a PBX software vendor labelled isp_telco.
Entity resolution is a heuristic Shortest-domain-wins picks the anchor, ~26% of records have no resolvable domain, and host count is a poor size proxy.
Only 3,000 of 43,577 queued entities are classified Budget. Everything below the cut stays U - unclassified and never reaches a rep.

The pattern worth naming

Three of the four bugs that mattered were found by reading output, not by running tests. Hosting providers in tier A, an IP address as a company, an email blaming a web server for a glibc vulnerability. Schema tests verify that data has the right shape. They cannot tell you the shape is describing the wrong thing.

What I would do differently

#Change
1Run the queue on the Batch API. 50% of standard rates with caching still applied — ~$80 a refresh against $161. Classification is the textbook workload. The architecture document asserted batch while the code only did the synchronous loop; a design that exists only in the prose is not a design.
2More evidence, not better prompting. The consistent failure is single-host entities with unfamiliar names. The model gets one host, a product string and an org name belonging to someone else. Page titles or WHOIS would fix most of it; no amount of prompt work will.
3150+ examples and a second labeller, with disagreements adjudicated.
4Repeated-run confidence intervals in the harness. We measured self-consistency by accident; the tooling should report an interval, not a point.
5Set tier thresholds from the distribution — a percentile cut decided in advance. Not retuned after the fact, because adjusting a threshold once you have seen which rows it moves is the same error as tuning a prompt after seeing its eval.
6Carry product and CVE as one struct through aggregation, so the Apache/glibc class of error becomes impossible rather than reworded around.

Overview / Scaling to 10×

89M records · ~740 GB

Scaling to 10×

89 million records, ~740 GB decompressed. Two layers already hold, two need restructuring, one changes character entirely — and the real bottleneck is accuracy, not compute.

LayerAt 10×
Ingest Design holds, parallelism doesn't. Memory is already flat. But a single-threaded parse turns 40 minutes into ~7 hours. Have the producer write many smaller zstd files and run one worker per file — embarrassingly parallel. The filesystem-glob resume state also needs a manifest with per-shard row counts.
Storage & compute DuckDB stops being the right tool. Correct for this exercise, wrong at 10×: it is single-node, and ~150–200 GB of Parquet will not aggregate comfortably in memory. Same models, different engine — Snowflake or Spark with dbt on top. Putting the business logic in dbt is what makes that migration cheap: swapping the adapter changes the warehouse, not the logic. Partition by country and scan date; make the entity and signal models incremental on scanned_at.
Entity resolution The real bottleneck — and it is about accuracy, not speed. The compute scales fine; the problem does not. 26% with no resolvable domain becomes ~650,000 unattributed hosts, wrong anchors multiply in absolute terms, and cross-TLD fragmentation grows. At this size I would stop treating it as string manipulation: ASN-to-organisation reference data to attribute domainless hosts, plus blocking-and-similarity matching to merge a company across TLDs. That is a real entity-resolution system rather than a public-suffix lookup, and it is where the engineering budget should go.
LLM layer Economics change, architecture mostly holds. 43,577 queued becomes ~435,000 — ~$1,600 on-demand, ~$800 batched. Batch becomes non-negotiable; add two-tier routing with Haiku for clear cases and Sonnet for ambiguous ones (measured, not assumed — this project is a case study in rankings inverting on more data); use the 1-hour cache TTL, since batch scheduling can outlast the 5-minute default. The signal filter matters more, not less — it already prevents 83,464 calls.
Serving Changes character completely. A 350 KB Parquet in git is right for a demo and absurd at ~1 million prospect rows. This becomes a served query layer — Postgres or DuckDB-over-object-storage behind an API, paginating server-side. And the app needs auth, which it does not have today.

The things that get worse faster than linearly

The eval set. 75 examples is already small. At 10× the population is more diverse — more countries, more regional providers — so a fixed-size eval covers proportionally less. It needs stratified sampling by region and estate size, and re-labelling as the data drifts.

Prompt drift. A prompt tuned on this snapshot degrades as the population shifts. At recurring 10× scale the eval belongs in CI, scoring every prompt change against a held-out set automatically.

The seed list. ~70 hand-curated patterns covering what was visible in this snapshot, with nothing refreshing it. Derive it from ASN ownership data instead of string matching.

Cost monitoring becomes mandatory. At $161 a refresh you can eyeball it; at $1,600 you need a budget guard that halts the run. The degradation path is documented — fall back to rules-only tiering, queue the remainder, alert — but it is not implemented.
